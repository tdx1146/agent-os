- **指令来源**：dandan 2026-09-23 修复单「给 v2 写自己的开机自启 + 退役 v1 自启入口」

- **备份**：`retired/start_all.sh.bak-20260923-1545`（移动前原件副本）

## 为什么退役

1. **抢 :19000 的元凶**：该 `@reboot`（v1 全栈）与 v2 `glue-watchdog.sh`（每分钟）竞态抢 `:19000`。
   2026-09-23 10:26 v1 抢先 → v2 `uvicorn glue.server:app` 绑不上端口退出；watchdog 只探"端口活着"故不再纠正
   ⇒ `:19000` 就一直被 **v1 `glue_server.py`（pid 10108）** 合法占住。
   （根因见 `/tmp/回执-glue切v2-20260923.md` §六.1）
2. **重启回退隐患**：只要这条 `@reboot` 还在，机器一重启 v1 glue 又会抢回 `:19000`。
3. **v2 已有自己的入口**：`agentos-v2/deploy/boot_v2.sh` + `@reboot`（同 sleep 20 槽位）。

## 它原来起了什么 → 现在谁接管

| 原 start_all.sh 起的东西 | 退役后谁负责 |
|---|---|
| 沙漏 HTTP API `:17333` | **`boot_v2.sh` 保底段**（`BOOT_V2_ENSURE_SANDGLASS=1`，默认开）；另有 v2 glue 6 线门禁盯着 |
| v1 LMS `:8190`（`api.run`） | crontab `@reboot sleep 30 lms_ctl.sh start`（**保留**，见下） |
| v1 glue `:19000`（`glue_server.py`） | **`boot_v2.sh`** 起 **v2 glue**（`glue.server:app`）；watchdog `glue-watchdog.sh` 兜底 |
| iso-sand scheduler/consumer | 早已停用（脚本内注释，V2 小脑/bus 接管） |
| 玄鉴 verify_daemon | 早已长期未跑（存量问题，Phase2 changelog 记录"暂不恢复"） |

## 一条命令回滚（恢复 v1 自启）

```bash
cp -p "/vol2/1000/AI专用/Agent OS/retired/start_all.sh.bak-20260923-1545" "/vol2/1000/AI专用/Agent OS/start_all.sh" 2>/dev/null; \
crontab -l | sed 's/^#@reboot sleep 20 && bash \/vol2\/1000\/AI专用\/Agent\\ OS\/start_all.sh/@reboot sleep 20 \&\& bash \/vol2\/1000\/AI专用\/Agent\\ OS\/start_all.sh/' | crontab -
```

> 更稳的回滚：直接 `crontab /tmp/crontab.bak-20260923-1545`（退役前整份 crontab 快照）
> 再把 `retired/start_all.sh` 移回根目录即可。**注意**：回滚后 v1 glue 会重新抢 `:19000`
> （与 v2 自启冲突），仅在你**确实要退回 v1 体系**时使用。
