基于 OpenClaw 源码能做什么改造？——记忆系统与认知架构深度改造指南

OpenClaw（MIT 许可，TypeScript/Node.js，~250k GitHub stars）的设计哲学是 "极简核心 + 插件化扩展"，这意味着它对改造非常友好——但改造的深度取决于你想动哪一层。下面从可改造边界 → 具体方向 → 实操路径逐层拆解。

一、先搞清楚：OpenClaw 当前的"记忆"和"认知"长什么样

现有记忆架构（四层栈）

层级 实现 本质

L1 会话上下文 JSONL transcript，当前会话完整交互记录在 context window 内 活体工作记忆（易失）

L2 每日日志 memory/YYYY-MM-DD.md，追加写入，今天+昨天自动加载 短期情景记忆

L3 长期声明性记忆 MEMORY.md（Markdown 纯文本），Agent 自己写进去 人工维护风格的语义事实库

L4 语义向量检索 SQLite + embeddings（OpenAI/Gemini/Voyage），混合搜索（BM25 + 向量 + MMR） 模糊联想检索层

外加一个实验性的 Dreaming 机制——后台对短期信号打分、筛选、提升到 MEMORY.md，带人工审查（DREAMS.md）。

现有认知模式

OpenClaw 的 Agent Runtime（pi-embedded-runner）走的是经典的 ReAct 式工具调用循环：组装上下文 → 调模型 → 解析 tool_use → 沙箱执行 → 结果注入 → 再调模型。上下文组装是一条优先级+Token预算管理的流水线（系统提示词 → 对话历史 → 记忆检索 → Skill 上下文 → 工具定义）。

一句话点破它的天花板：当前 OpenClaw 的记忆本质是 "检索增强的文件系统 + 向量搜索"，而不是真正的认知架构。它没有结构化的遗忘、没有因果追踪、没有心智状态建模——这些都是你可以再造的空间。

二、改造的三个层次（从安全到激进）


┌─────────────────────────────────────────────────────┐
│  Level 1 — 配置层改造（零代码，改 YAML/json5）        │  ← 最安全，随时回退
│  Level 2 — 插件/Plugin 层改造（写 TS 模块挂进钩子）   │  ← 推荐的主战场
│  Level 3 — Runtime 核心改造（改 pi-embedded-runner）   │  ← 激进，需跟进上游
└─────────────────────────────────────────────────────┘


🔧 Level 1：配置层 —— 先榨干原生能力

不改代码就能做的：

• 调记忆检索策略：切 hybrid search 权重、开 MMR 多样性重排、开时间衰减（temporalDecay），控制向量/text 比例、候选池大小

• 改 compaction 触发阈值和 memory flush prompt：在对话压缩前用什么"话术"提醒 Agent 沉淀记忆，直接影响长期记忆的信噪比

• 换 memory backend：从内置 SQLite 切到 QMD sidecar（支持重排序、查询扩展）或接 Honcho（AI 原生跨会话 memory，用户建模）

• 开 Active Memory 插件：让一个子代理在每次主 Agent 回复前预检上下文、自动注入相关事实——等于加了一层"主动回忆"机制而非纯被动检索

这一步的价值常被低估。先把 compaction prompt、检索阈值、时间衰减调好，再谈造轮子。

🔧 Level 2：插件层 —— 再造记忆系统的主战场

OpenClaw 有 Plugin 体系 + Hooks + 自定义 Skill + 自定义 Memory Plugin 的扩展口。这是最合理的改造层——不 fork 核心也能深度替换行为。

改造方向 A：把"文件系统记忆"升级为结构化记忆图谱

现有 MEMORY.md 是无结构的 Markdown 段落。你可以写一个 自定义 memory plugin 替换/增强 memory-core：

你要加的东西 怎么挂进去

实体-关系图谱（人/项目/概念/决策之间的边） 在 memory_search 返回结果里做图遍历扩召回；或用独立图 DB（Neo4j/SQLite 的 json1 扩展存边表）

带时间戳+置信度的三元组（S,P,O,T,confidence） 重写记忆写入：Agent 写记忆时不 append 自由文本，而是走一个 extractor（可用小模型抽取 (subject, predicate, object)），存结构化表

引用溯源（这条记忆从哪个对话/文件来） 每条记忆条目加 source: { type: 'chat', timestamp, sessionId, excerpt }

冲突消解（Agent 在不同时间学到矛盾信息） 加版本链 + 置信度衰减，检索时做时序仲裁

实操路径：参考 memory-core 插件的接口契约（provider 模式），在 ~/.openclaw/ 的 plugins 目录下写你的 memory-graph 插件，实现 memory_search / memory_get / recall / promote 钩子，然后在 config 里切 memory.provider: "graph"。

改造方向 B：引入真正的遗忘机制（不止是时间衰减）

当前只有 temporalDecay 做分数衰减，没有主动遗忘。你可以设计：

遗忘策略 思路

Ebbinghaus 式衰退 每条记忆有 strength，每次 recall 成功则强化，长期不 recall 则 strength ↓，低于阈值的标记 stale

重要性锚定 用户显式说"永远记住"→ pinned: true 免衰；Agent 自评重要性得分 < 阈值 → soft delete

容量触发的 LRU 淘汰 长期记忆文件大小/条目数超过 budget 时，淘汰最低效用分（效用 = 频次 × recency × importance）的条目

语义去重合并 写新记忆前做 embedding 相似度比对，相似度高则 merge 而非 append，避免 MEMORY.md 膨胀成垃圾堆

核心思路：把 MEMORY.md 从一个 append-only 日记本变成一个 managed knowledge base。

改造方向 C：再造记忆模式——Episodic / Semantic / Procedural 三分法

心理学里人类记忆分三类中的 memory-wiki 插件其实在往"知识库"方向靠，但它仍然是 flat wiki。你可以显式分区：

workspace/
  memory/
    episodic/     YYYY-MM-DD.md（保留原始情景流）
    semantic/     facts.db 或 facts.md（结构化断言库）
    procedural/   SOPs/   （怎么做事的技能级记忆 → 可以跟 Skills 体系联动）
    index.sqlite  （统一的向量 + 图索引）


然后改 上下文组装流水线（见下文 Level 3 也可在插件层 hook）让 Agent 在不同场景下激活不同记忆域：
• 聊"上次开会说了啥" → 偏向 episodic

• 聊"我们的技术栈偏好是什么" → 偏向 semantic

• 聊"怎么部署这个项目" → 偏向 procedural（SOP 检索）

改造方向 D：Active Memory 子代理进阶 —— 做成反思循环（Reflection Loop）

当前的 active-memory 插件只是每次回复前做一次检索注入。你可以把它升级为：

用户消息到达
  → Active Memory 子代理：检索 + 提炼 relevant facts
    → 写入一个短暂的结构化「工作记忆区」（本轮对话的 scratchpad）
      → 主 Agent 读取 scratchpad 作为"当前心智状态"
        → 回复完成后：子代理再做一次 reflection（学到了什么新事实？矛盾吗？要更新记忆吗？）


等于给了 Agent 一个 System 1 / System 2 的两层认知：
• System 1 = 主 Agent（快速反应、工具执行）

• System 2 = Memory 子代理（慢速反思、记忆整合、一致性校验）

🔧 Level 3：Runtime 核心改造 —— 动 pi-embedded-runner

如果你想再造的是 认知理解模式本身（而不只是记忆存储），就需要碰 Agent Runtime。核心文件在 src/agents/pi-embedded-runner/。

你能改什么：

认知能力 改哪里 怎么做

Tree of Thoughts（ToT） 替代线性 ReAct 工具调用循环 让模型生成多个候选 plan → 各自 rollout 一步 → 评分 → 回溯/选择（需要一个 evaluator LLM call）

Self-reflection / Critique 循环 在 tool execution 之后、下一轮 model call 之前插入 Agent 产出结果 → reflection prompt 让模型自检（"这个结论有支撑吗？有没有遗漏？"）→ 修正或继续

心智状态（Belief State）建模 上下文组装流水线 不再只拼 raw history，而是维护一个结构化 beliefState: { goals[], facts{}, uncertainties[], contradictions[] }，每轮更新后序列化进 prompt

注意力/上下文预算管理策略 allocateTokenBudget 逻辑 把固定的 50%/30%/20% 改成动态调整：根据 query 类型（检索型 vs 执行型 vs 闲聊型）弹性分配 token

⚠️ Level 3 的风险：你开始 fork 核心逻辑，上游更新（OpenClaw 迭代极快）会产生 merge conflict。务实做法是用 wrapper/HoC 模式：不改原文件，在你的插件里 intercept（如果作者留了 hook point），或维护一个 patchset。

四、实操建议（帮你少踩坑）

1. 先 fork 读代码，不要急着写：重点读 src/agents/pi-embedded-runner/（执行循环）、src/gateway/（消息路由与会话状态机）、以及 memory plugin 的 interface 定义。OpenClaw 的代码组织是"单进程 Node.js + 显式目录约定"，上手不算难。

2. 记忆改造的第一优先级是信噪比，不是复杂度。绝大多数 OpenClaw 实例的 MEMORY.md 最后会变成无人维护的臃肿文本墙。一个简单的 （结构化提取 → 去重合并 → pinned 锚定 → 衰减淘汰） 四件套，收益远大于上图数据库。

3. 别试图让 Agent "真正理解"——LLM 的"理解"永远是统计模式匹配。你能做的是给它更好的 信息结构、检索精度、一致性校验和状态追踪。把这些做实，体验上就会从"随机应变"变成"有据可依"。

4. 如果目标是研究性质的认知架构实验（比如 ToT、belief state、元认知），反而建议你以 OpenClaw 的 Channel + Gateway + Skill 执行沙箱 为基础，但把 pi-embedded-runner 的 ReAct loop 替换为你自己的 runner（保持接口兼容：(messages, tools, workspace) → { response, toolCalls }），这样既不跟上游死绑，又能复用它的消息管道和沙箱。

如果你告诉我：你想让 Agent 具体"表现得更像什么"（比如"像一个有连续自我感的私人秘书" vs "像一个有论证能力的科研助手" vs "像能反思错误的编程搭档"），我可以把改造方案收敛到一套更具体的模块清单 + 需要动的文件路径级别。

### 三条改造路径（2026-05-24 16:50 讨论结论）

三者不互斥，最终都要走。

#### 路径 A：继续用注入脚本（已有的 HTTP 编辑器 + inject_via_websocket）
- 已在运行
- 负责：守夜脉冲、文件变更监控、轮感写 memory
- 缺点：依赖独立的 Python 服务器，需要维护

- OpenClaw 原生支持，不需额外配置

- 子代理是**完全独立的会话**，有自己的上下文，完成后结果推回主会话
- 每轮额外 token 开销约 ¥0.003
- 可代替注入脚本的部分功能（读 today.log、提取摘要）
- 子代理对话用户不可见，只有最终结果推回

#### 路径 C：改 memory flush prompt
- 改 JSON 配置（`agents.defaults.compaction.memoryFlush`）
- 让压缩前的记忆沉淀变成结构化的三行：
  - `📁 本轮文件变更`
  - `🌫️ 本轮轮感`
  - `🔗 本轮提到的关键概念`
- 零代码，五分钟可做完
- 只解决压缩场景，不覆盖每轮

你的直觉很准，“记忆力”在这里确实有两层含义：底层大模型的瞬时记忆（Context Window）和上层 Agent 框架的长期记忆（Memory System）。Hermes 被称“最强”，赢在后者。

至于 OpenClaw 里 DeepSeek V4 只有 200K，纯粹是配置文件的“保护性”默认值导致的，并非模型能力问题。

一、Hermes Agent 与 OpenClaw 的本质区别

这两者不是同一个维度的产品。OpenClaw 是“全能工具箱”，Hermes 是“自进化大脑”。

维度 OpenClaw (龙虾) Hermes Agent
核心定位 多模态、多通道的任务执行器 具备学习闭环的自主智能体
记忆哲学 全量记录：把所有日志、文件当记忆存下来，偏向流水账  分层精选：SQLite + 检索 + 摘要，只把精华提炼进上下文 
技能获取 人工编写：Skill 靠人写，稳定但上限受限于开发者  自动沉淀：任务完成后自动生成 Skill，越用越强 
体验差异 像雇佣了一个听话的熟练工，你指哪打哪 像培养一个会成长的学徒，它慢慢懂你的习惯

为什么说 Hermes 记忆力强？

不是因为它能塞更多 Token，而是因为它有“记忆-反思-进化”的闭环。它会自动把历史对话提炼成 
"MEMORY.md" 和 
"USER.md"，跨会话记住你的项目细节和代码风格，下次无需重复解释 。OpenClaw 虽然也能存，但缺乏这种自动的“消化”机制。

二、DeepSeek V4 在 OpenClaw 里变“失忆”的真相

你提到的“DeepSeek V4 宣称 2M 上下文，OpenClaw 里只有 200K”，这是一个非常典型的配置坑。

1. 原因：安全默认值

OpenClaw 对于未知/自定义模型，出于防止爆窗的保守策略，会强制使用一个较低的默认上下文窗口（通常是 200K），而不是自动探测模型的最大能力 。

2. 解决方案：手动修正配置

DeepSeek V4 的实际上下文能力远超 200K（Flash 版支持 1M，Pro 版支持 2M）。你需要手动在 OpenClaw 的配置文件（
"openclaw.json"）中显式声明：

{
  "models": {
    "deepseek-v4-pro": {
      "contextWindow": 2000000,  // 手动改为 2M
      "maxTokens": 131072
    }
  }
}

改完重启 OpenClaw，它就会释放模型真正的长文本能力 。

三、关于“记忆力取决于大模型”的澄清

你的理解完全正确，Agent 框架无法突破底层 LLM 的物理极限。

- 大模型负责“瞬时记忆”：单次对话能“记住”多少内容，完全由 DeepSeek、GPT 等模型的 Context Window 决定。这是硬件和推理成本的硬限制。
- Agent 负责“长期记忆”：框架的作用是跨会话的记忆管理。通过数据库、检索和摘要，把“过去发生的事”在“当前对话”中重新喂给大模型，模拟出“记得之前聊过”的效果 。

结论：Hermes 的“强记忆力”指的是它管理长期记忆的机制更智能（自动提炼、分层），而不是它能把 2M 的模型变成 4M。
