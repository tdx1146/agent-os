## ③ 发现的问题（按严重度排序，含证据）

### P1 🔴 唤醒链主通道（B 通道 chat.send）当前故障：`GATEWAY_TOKEN not found`
- 证据：`sandglass/metrics.jsonl` 17:10/17:20/17:30/17:40/18:00/18:10/18:40/19:10/19:20 共 9 次 `"reason": "wake_failed:inject_exit_1: Warning: GATEWAY_TOKEN not found. Set env var..."`；13:32 代码注释「B 通道 chat.send → 必然触发一次 run → 主 AI 真正看到」。
- 根因链（源码实据）：wake_client.wake_editor() 以 subprocess 调 inject-helper.mjs，**未传 OPENCLAW_HOME/GATEWAY_TOKEN**；crontab 环境无 OPENCLAW_HOME → inject-helper 的 findOpenClawHome() 落到错误默认路径 → 读不到 openclaw.json 的 gateway.auth.token → 空 token → WebSocket 认证失败 exit 1。对比：edit-web.py 自己解析 OPENCLAW_HOME/GATEWAY_TOKEN 所以守夜/自问链路是好的。
- 影响：13:32 切换后，B 通道**至今一次都没成功投递过**。

### P1' 🔴（与上相关但更重要）A 通道其实已经够用，B 通道不是必需
- 证据：19:34 wake 事件 2 分钟内被 19:36 心跳消费；此前「20+ 次 200 零注入」的根因是 **heartbeat 默认 target:none（不投递）**，不是 A 通道本身坏。今天 target:last 修好后，A 通道 = 事件入队 ≤30min 被心跳拾取 + 主 AI 可选择投递。B 通道（chat.send 强制立即 run）只是「更快」，且目前是坏的。
- 结论：二选一——修 B（一行 env）或回退 A 为主。见 ④。

### P2 🟠 进程双实例复发（8/4 Phase 6 清理过的同类问题）
