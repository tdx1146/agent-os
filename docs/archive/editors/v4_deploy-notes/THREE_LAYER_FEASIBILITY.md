## 1. 单 session 三层共存模型

### 1.1 三层定位

| 层 | 角色 | 运行时 | 模型选择 | 上下文焦点 |
|----|------|--------|----------|-----------|
| **沟通翻译层** (L1) | 前台助理 | 主 session（常驻） | DeepSeek V4 Flash | 当前对话轮次、用户意图、最近断言 |
| **自我认知层** (L2) | 后台经验蒸馏 | 子代理（按需/cron 触发） | Astron / 混元 hy3 | facts.dict.md 全量、MEMORY.md 全量、近日日记 |
| **自我审计层** (L3) | 后台质量监控 | 子代理（cron 触发） | 混元 hy3（视野宽，不易误判） | 最近 N 轮完整上下文、facts.dict.md 断言一致性 |

### 1.2 各层需要的上下文内容

**L1 沟通翻译层（主 session）**
- AGENTS.md / SOUL.md（启动注入）
- facts.dict.md 头部（事实索引部分，非断言全文）
- memory/YYYY-MM-DD.md 今天+昨天的轮感（精简版）
- 最近 2-3 条消化断言（assertion 路标而非全文）
- 用户当前消息 + 对话历史（最近 5-10 轮）
- **不加载**：全量 facts.dict.md 断言（~200+ 条，token 浪费）
- **不加载**：history/ 完整存档

**L2 自我认知层（子代理）**
- facts.dict.md **全量**（所有断言 + 置信度标记 + META 模式）
- MEMORY.md **全量**（长期记忆 + 情感边界 + 跨实例协议）
- yesterday.md + today.md 完整轮感
- knowledge-tree.md（若有）
- 主代理交付的任务："从近期对话中蒸馏经验，更新 MEMORY.md"

**L3 自我审计层（子代理）**
- 主 session 最近 3-5 轮对话全文（需从备份或 RPC 获取）
- facts.dict.md 断言列表（检查最近输出是否匹配已知断言）
- tools.md 中的工具调用记录
- 主代理交付的任务："检查最近输出中的幻觉迹象、代码污染、上下文膨胀程度"

### 1.3 层间共享信息机制

```
┌────────────────────────────────────────────────────────┐
│                  主 session (L1)                        │
│                                                        │
│  用户消息 → 读事实(头部) + 读轮感 → 回复 → 通知 L2/L3 │
│                                                        │
│  持久化动作：                                            │
│  ├─ facts.dict.md 追加新断言                           │
│  ├─ memory/YYYY-MM-DD.md 追加轮感                      │
│  └─ 触发指令："/spawn L2 蒸馏" 或 "/spawn L3 审计"     │
└──────────┬──────────────────────────────────┬───────────┘
           │ 通过文件                            │ 通过文件
           ▼                                    ▼
┌───────────────────┐             ┌──────────────────────┐
│ L2 子代理         │             │ L3 子代理             │
│ 读记忆+断言 →      │             │ 读上下文+断言 →       │
│ 更新 MEMORY.md    │             │ 写审计报告            │
│ 更新 persona.md   │             │ 建议清除/保留          │
│ 写 insight/       │             │ 标记可疑输出           │
└───────────────────┘             └──────────────────────┘
```

**关键设计原则：文件是唯一的层间通道，session 内变量不跨层。**

原因：
- 子代理是独立 session，主 session 变量对他们不可见
- 文件持久化天然抵抗 session 截断和重启
- 文件修改历史可审计（diff / git log）

## 2. 缓存冲突分析

### 2.1 DeepSeek Prompt Caching 工作机制

DeepSeek 的 prompt caching 基于 **prefix matching**（前缀匹配）：

```
缓存命中的条件：
  当前请求的 messages 数组的前缀（从头开始的连续序列）
  与之前某个请求的前缀完全一致
```

工作细节：
1. 缓存粒度是 **messages 数组的连续前缀**，从 system message 开始
2. 命中的片段 token 成本降低（约 90% 折扣）
3. 缓存有 TTL（通常数分钟，活跃命中后刷新）
4. 跨 API key 的缓存**隔离**——不同 key 不共享缓存
5. 模型版本不同时缓存也不共享

**关键特性**：缓存匹配是严格的字节级前缀匹配。只要前 N 条 message 的 content 完全相同，就命中缓存。任何微小的差异（一个空格、一个换行符不同）都会导致缓存 miss。

### 2.2 为什么子代理用 DeepSeek 会污染主代理缓存

子代理 session 的 messages 结构完全不同：

```
主代理消息序列（DeepSeek 主模型）：
  [system(AGENTS.md+SOUL.md+...), user(L1上下文), assistant(回复), ...]

子代理消息序列（如果也用 DeepSeek 且同 API key）：
  [system(子代理 system prompt), user(L2任务), assistant(子代理回复), ...]
```

**污染路径**：
1. 子代理请求的前缀（system prompt）完全不同 → 不共享缓存命中
2. 更糟的是，子代理的请求**创建了新的缓存片段**，而这些片段对主代理毫无价值
3. 如果同时使用**同一个 API key**，缓存空间被稀释——主代理的常用缓存片段可能被子代理的不相关缓存片段**挤出缓存**（缓存容量有限）
4. 缓存碎片化导致主代理每次请求都需要重新计算前缀中的重复片段

**量化评估**：
- 当前轻如烟主 session 每轮 token 约 8K-20K（含注入文件）
- 缓存命中的收益约 5K-15K token（按 90% 折扣 = 可忽略成本）
- 但关键是**响应延迟**——缓存 miss 导致首 token 时间（TTFT）增加 1-3 秒
- 对 dandan 的对话体验而言，延迟增加比 token 成本更致命

## 3. 三层间的 data flow

### 3.1 完整流程

```
┌─────────────────────────────────────────────────────────────┐
│ [Session Start]                                              │
│                                                              │
│ ┌─────────────┐                                             │
│ │ L1 沟通翻译层 │  ← 用户消息输入                            │
│ │ (主session)  │                                             │
│ └──────┬──────┘                                             │
│        │                                                     │
│        ├─ 1. 读 facts.dict.md 头部（事实索引，非断言全文）     │
│        ├─ 2. 读 memory/YYYY-MM-DD.md（今天轮感）             │
│        ├─ 3. 处理用户意图，选工具/direct reply                │
│        │                                                     │
│        ├─ 事实确认 → 写入 facts.dict.md 追加                 │

│        │                                                     │
│        ├─ 经验确认 → 写入 memory/YYYY-MM-DD.md 轮感          │

│                                                              │
│ ┌─────────────────────────────────────────────────────┐      │
│ │ L2 认知层（子代理 session，Astron）                   │      │
│ │                                                      │      │
│ │  1. 读全量 facts.dict.md（断言 + META）               │      │
│ │  2. 读全量 MEMORY.md（长期记忆）                      │      │
│ │  3. 读近日日记（today.md + yesterday.md）             │      │
│ │  4. 蒸馏经验，浓缩为：                                │      │
│ │     ├─ MEMORY.md 追加新记录                           │      │
│ │     ├─ facts.dict.md 追加高阶断言                     │      │
│ │     └─ persona.md 更新 dandan 画像                    │      │
│ │                                                      │      │
│ │  输出：写入完成报告到临时文件（如 /tmp/l2-report.md）  │      │
│ └─────────────────────────────────────────────────────┘      │
│              ↑ session_spawn                                  │
│              ↓ cron 或 L1 通知                               │
│ ┌─────────────────────────────────────────────────────┐      │
│ │ L3 审计层（子代理 session，混元 hy3）                  │      │

│ │  1. 检查 L1 最近输出中的事实性断言是否与                 │      │

│ │  2. 标记疑似幻觉（格式：一致性得分 + 证据链）           │      │
│ │  3. 评估 context 膨胀程度 → 建议清除/保留轮次          │      │
│ │  4. 检查代码污染：子代理的任务描述中                     │      │
│ │     是否混入了 L1 的 prompt 规则                      │      │
│ │                                                      │      │
│ │  输出：审计报告到 auditor/ 目录                        │      │
│ └─────────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 触发条件

| 层 | 触发方式 | 频率 | 交付物 |
|----|---------|------|--------|
| L1 | 用户消息驱动 | 每次对话 | 回复 + 当日轮感追加 |
| L2 | L1 session 结束前 / cron 定时 | 每 4-6h 或 L1 主动触发 | MEMORY.md 更新 + 断言升格 |
| L3 | cron 定时 / L1 怀疑输出质量时 | 每 8h 或定期 | 审计报告（文件写入） |
| L1→L2 触发器 | L1 写入"关键经验"标记 | 事件驱动 | `/tmp/trigger-l2.txt` 标记文件 |
| L1→L3 触发器 | L1 发现输出可疑 / 审计 cron | 事件驱动 + 定时 | `/tmp/trigger-l3.txt` 标记文件 |

## 4. "主动遗忘"的实现机制

### 4.1 核心问题

主 session 中，事实写入 facts.dict.md 后，**不应在下一轮对话中主动引用这些事实**，否则：
- 对话聚焦被分散到"证明我知道某事"而非处理当前问题
- 上下文膨胀（facts.dict.md 当前 ~200+ 断言，全量注入浪费 token）
- 违背 dandan 的"不在台面上放太多"的情感边界哲学

### 4.2 主动遗忘的分层策略

```
┌──────────────────────────────────────────────────────┐
│ 主 session（L1）的上下文控制                            │
│                                                        │
│  每次启动读：                                           │
│  ├─ facts.dict.md 头部（~20行，事实索引）               │
│  ├─ 最近 2-3 条消化断言（路标级，非全文）                │
│  └─ 今天+昨天轮感（精简版，不含句子级细节）              │
│                                                        │
│  不主动读的：                                           │
│  ├─ facts.dict.md 中带 ✅✅ 的已确认断言（"记住但   │
│  │  不引用"）                                          │
│  ├─ 超过 24h 的断言（"自动遗忘"）                      │
│  └─ MEMORY.md 主体（L2 维护，L1 只在需要时按需读）     │
└──────────────────────────────────────────────────────┘
```

### 4.3 为什么不能靠 system prompt 修改

关键限制：
- system prompt 通过 `before_prompt_build` 插件注入，**每次模型调用一个独立 prompt**
- 如果尝试加指令"facts.dict.md 中带 ✅✅ 的断言不主动引用"，这个指令本身就占用 token
- 更严重的是，AGENTS.md 每次都注入，内容不可变——不能通过修改 AGENTS.md 来动态控制"本条已确认，请遗忘"

**结论：system prompt 适用于"常设规则"，不适用于"动态遗忘标记"。**

### 4.4 推荐实现方案

#### 方案 A：facts.dict.md 分层结构（推荐）

将 facts.dict.md 分为三个区块：

```
# 事实字典 v3

## 📌 锚点区（L1 每轮必读）
- 名字：轻如烟
- 主人：dandan
- API 端点（不含 key）
- 关键路径

## 🧩 活跃断言区（L1 有选择地读）
- 最近 24h 的新断言（未升格）
- 本章节末尾标记 `## LAST_ACTIVE_BOUNDARY`
- L1 在此行之前的内容选择性引用

## 📚 档案区（L2 全量维护，L1 不主动读）
- 全部已确认断言（带 ✅✅）
- META 模式
- 历史记录
```

**实现方式**：L1 每次启动时，从 facts.dict.md 读取到 `## LAST_ACTIVE_BOUNDARY` 行即停。
后面的档案区只在 L2/L3 子代理读取。

#### 方案 B：独立标记文件

创建一个 `forget-index.md` 控制"不再主动引用"的内容：

```markdown
# 遗忘索引

## 以下内容已确认入档，L1 不主动引用：
- R1-R10 系列断言（已入库，不再提起）
- 武器库对线结果（memory/MEMORY.md 中已有存档）
- 具体技术修复记录（除非当前问题相关）

## 以下内容仍活跃，L1 可引用：
- 最近 24h 新追加断言
- 用户今天明确提及的话题
- 跨 session 持续未完成的待办
```

**优点**：显式控制，人类可读
**缺点**：多一个文件要维护

#### 方案 C：断言置信度 + 时间戳双维过滤

在 facts.dict.md 的断言格式中加入时间戳字段，L1 启动时自动过滤：

```markdown
| # | 断言 | 置信度 | 时间 | 引用策略 |
|---|------|--------|------|---------|
| F1 | 编辑器的xxx问题根因是... | ✅✅ | 2026-06-01T03:00 | archive（不主动引用） |
| F2 | 今天发现的xxx bug... | ⏳ | 2026-06-25T19:00 | active（可引用） |
```

**L1 启动时的过滤逻辑**：
1. 引用策略 = `active` 的 → 载入
2. 引用策略 = `archive` 的 → 跳过
3. 引用策略为空但 < 24h → 载入
4. 引用策略为空且 > 24h → 自动标记为 `archive`

### 4.5 子代理认知报告替代主 session 上下文的可行性

**评估：可行，但有边界条件。**

```
L1 session 结束前触发 L2
  └─ L2 读取 L1 的完整轮感
  └─ L2 蒸馏后更新 MEMORY.md
  └─ L2 写入 "认知简报"：对 dandan 是极简结论

下一轮 L1 session 启动
  └─ 读 L2 的认知简报（3-5 行极简结论）
  └─ 不读 L2 所依赖的原始材料（日记/断言全量）
```

✅ **可替代的部分**：
- 技术细节的记忆（编辑器修复步骤、API 端点变更）
- 长序列对线结论（武器库对线结果）
- 日常轮感的低价值信息（"深呼吸一下"等状态记录）

❌ **不可替代的部分**：
- 用户今天刚说的、尚未蒸馏的上下文
- 当前对话的即时依赖（dandan 正在讨论的事）
- 安全阀规则和情感边界（必须 L1 自己读）
- dandan 的情绪状态和语气（L2 蒸馏会丢失）

**实际效果**：
- L1 上下文可减少约 30-50%（减少全量断言和日记的注入）
- 代价：L2 的蒸馏质量决定了 L1 的"记忆准确度"
- 底线：永远保留直接从文件读取原始信息的能力（不依赖 L2 蒸馏）

## 5. 风险点

### 5.1 层间状态不一致

**场景**：L2 更新了 MEMORY.md，但 L1 读到的是旧版本。

| 风险 | 概率 | 严重度 | 缓解措施 |
|------|------|--------|---------|
| L2 刚写完 MEMORY.md，L1 已启动 | 中 | 高 | L1 启动时总是读最新文件，不缓存 |
| L2 写入过程中 L1 同时读取 | 低 | 中 | 写操作使用临时文件 + rename（原子写入） |
| L1 写日记时 L2 同时读 | 低 | 高 | L1 写日记应在 L2 触发前完成 |
| L1 写断言时 L2 同步读 | 中 | 中 | L2 启动前等待 L1 标记"写入完成" |

**系统级缓解方案**：

```bash
# 原子写入模式（L1 和 L2 都应遵循）
write temp file → mv temp to target → fsync dir

# 避免同时读写
L1 写操作优先（文件锁语义）
L2 启动前检查 facts.dict.md 的 mtime 是否 > 2s（确保写入完成）
```

### 5.2 审计层误判

**场景**：L3 将正确的输出识别为幻觉。

**根因分析**：
- L3 读不到完整的 L1 推理链（只有最终输出）
- L3 的 context window 限制导致只看片段
- L3 模型（推荐混元 hy3）可能对某些领域知识不足

**缓解措施**：

| 措施 | 实现方式 | 效果 |
|------|---------|------|
| 置信度分级 | L3 输出用"疑似/确认/高危"三级，不直接标记"幻觉" | 降低误判容忍成本 |
| 举证要求 | L3 必须引用 facts.dict.md 行号作为证据 | 可追溯，可复核 |
| 影子判据 | L1 自己对输出质量做量化评分（0-5），与 L3 结果交叉验证 | 冲突时以 L1 自评 + L3 证据综合裁决 |
| dandan 裁决 | 所有"确认幻觉"标记需 dandan 当面确认才生效 | 终极防误判 |

**推荐阈值**：
- 一致性得分 ≥ 0.8 → 正常，不标记
- 0.5 ≤ 得分 < 0.8 → 标记为"需关注"，不告警
- 得分 < 0.5 → 标记为"疑似幻觉"，附带完整证据链，写入 auditor/ 目录
- **不得自动截断或回滚**——审计结果只是建议，决策权在 L1 或 dandan

### 5.3 Round-Trip 延迟

**场景**：L1 → spawn L2 → L2 读取文件 → L2 推理 → L2 写入 → L1 续接。

**实测数据**（从现有系统经验推断）：

| 操作 | 延迟 |
|------|------|
| sessions_spawn 子代理 | ~2-5s（Gateway RPC 通信） |
| 子代理读取全量 facts.dict.md（~200 断言） | ~1-3s |
| L2 蒸馏推理（Astron） | ~3-8s |
| L2 写入 MEMORY.md | <1s |
| **总延迟** | **~7-17s** |

**影响分级**：

| 场景 | 延迟容忍度 | 建议 |
|------|-----------|------|
| L1 session 结束时触发的 L2 | 高（用户已离开） | ✅ 可接受，后台运行 |
| 用户等待回复中触发 L2 | 低（用户在线等） | ❌ 不可接受，应异步处理 |
| cron 定时触发的 L2 | 最高（无用户等待） | ✅ 完全可接受 |
| L3 审计 | 最高（后台运行） | ✅ 完全不涉及用户等待 |

**缓解方案**：

1. **L2/L3 永远异步执行**——不在用户等待回复的过程中触发
2. **cron 调度优于 session 结束时触发**——避免"最后卡在 L2 上"
3. **状态标记文件**：L1 判断"有新的 L2 报告"时，在读入时加载，不等待 L2 运行
4. **超时兜底**：子代理超过 30s 无回复 → 标记为"此轮蒸馏跳过"
5. **多管道并行**：L2 和 L3 可以同时 spawn，不阻塞彼此

### 5.4 额外风险：L2/L3 子代理本身的质量

从现有经验看（facts.dict.md 中 GLM-Z1-Flash 被排除）：

**风险清单**：

| 风险 | 来源 | 概率 | 缓解 |
|------|------|------|------|
| 子代理输出低质 | GLM 被排除前例 | 中 | 主代理 L1 做整合过滤，不直接采用子代理结论 |
| 子代理"附和行为" | 已知行为模式 | 中高 | 子代理任务描述中加"你必须给出独立判断，和主代理不同意见更欢迎" |
| 子代理循环空转 | cron 调度中偶发 | 低 | 超时机制 + 连续两次无意义输出 → 标记降级 |
| 子代理消耗 API 配额 | Astron ¥19 包月，无限的 | 低 | Alias 价格便宜，注意监控 |
| 子代理产生毒性输出 | 安全层反跳 | 低 | L1 的整合过程本身就是安全过滤 |

### 5.5 风险汇总矩阵

| # | 风险 | 概率 | 影响 | 优先级 | 缓解负责人 |
|---|------|------|------|--------|-----------|
| R1 | L2 读旧版 L1 日记（时序竞争） | 🟡 中 | 🟠 中 | **P2** | L1 写完后打标记 |
| R2 | L3 误判正确输出为幻觉 | 🟢 低 | 🔴 高 | **P1** | 置信度分级 + 举证要求 + dandan 裁决 |
| R3 | L2/L3 延迟导致 L1 卡顿 | 🟡 中 | 🟠 中 | **P1** | 异步执行 + cron 调度 + 超时兜底 |
| R4 | 子代理模型不可靠（如 GLM） | 🟠 高 | 🟠 中 | **P1** | 选型时严格筛选 + L1 整合过滤 |
| R5 | 文件写入竞争（L1/L2 同时写同一文件） | 🟢 低 | 🔴 高 | **P1** | 原子写入 + 时序协调 |
| R6 | 子代理消耗主代理模型的缓存 | 🟢 低 | 🟢 低 | **P3** | 子代理选不同模型 + 不同 API key |
| R7 | facts.dict.md 过长导致 L1 启动慢 | 🟠 中 | 🟢 低 | **P3** | 分层策略（方案A），L1 只读头部 |

## 总结意见

### 可行性判断：✅ 可行

三层架构在单 session 内完全可行，但需要满足以下条件：

1. **模型隔离**：L1 用 DeepSeek（主），L2 用 Astron（子），L3 用混元 hy3（审计）。三者 API key 不同，缓存互不污染。
2. **异步执行**：L2/L3 永不阻塞 L1 回复，通过 cron 或 session 结束触发。
3. **文件通道**：层间信息唯一通过文件（facts.dict.md / MEMORY.md / 标记文件）传递，不依赖 session 变量。
4. **主动遗忘**：通过 facts.dict.md 分层结构实现——L1 只读头部 + 近期活跃断言，档案区由 L2 维护。
5. **审计安全网**：L3 输出置信度分级，不需 dandan 确认不生效，误判风险可控。

### 实施优先级

| 阶段 | 内容 | 工作量 |
|------|------|--------|
| P0 | facts.dict.md 拆分（锚点区/活跃区/档案区） | 小（文件结构重排） |
| P0 | L2 认知层子代理任务定义（Astron 模型） | 中（任务 prompt 编写） |
| P1 | cron 调度 L3 审计层 | 中（审计 prompt + 报告格式） |
| P1 | 原子写入机制保障层间一致性 | 小（写入封装） |
| P2 | L1 启动时选择性读取策略 | 中（AGENTS.md 更新） |
| P2 | L2 认知简报替代部分 L1 上下文 | 大（需调优质量阈值） |
| P3 | 审计误判的长期数据集积累 | 持续（经验驱动改进） |
