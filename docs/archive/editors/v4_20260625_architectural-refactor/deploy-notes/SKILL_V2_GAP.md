# 高级助理 Skill v2 草案 — 缺口分析报告

> 分析日期：2026-06-25
> 分析人：子代理（独立评审视角）
> 范围：仅分析草案正文，未引入外部上下文

---

## 1. 定义模糊的地方

### 1.1 "事实确认后" → 谁来确认？什么算确认？

**草案原文：** "事实确认后 → 记入 facts.dict.md"

**缺口：**
- 事实的"确认"标准未定义。是 dandan 口头确认？是跨来源交叉验证？还是自己觉得"像真的"就行？
- 确认主体缺失：是我自己确认，还是派子代理确认，还是等 dandan 确认？
- 没有区分"确认中"、"已确认"、"待验证"三种状态，导致 facts.dict.md 可能混入未经验证的猜测。

**建议：** 定义三级置信度——`[C0]不确定`（仅记录待验证）、`[C1]单源可信`（文件/日志来源）、`[C2]双源交叉`（至少两个独立来源或 dandan 明确确认）。只有 C2 才视为"确认"。

---

### 1.2 "上下文中归档" → 具体怎么做？

**草案原文：** "事实入字典后，主动在上下文中'归档'（不再主动引用）"

**缺口：**
- "归档"在操作层面完全不明：是指从当前会话上下文中用 `delete_messages` 清除？是指停止引用但保留在记忆中？还是指在 prompt 前缀中移除？
- "不再主动引用"的触发条件：入字典后立即停止？还是当前任务结束后？
- 重新入字典说、字典里已经有过的事实，何时可以被重新引用？
- 没有说明"归档"是否可逆——如果发现字典写错了，怎么找回？

**建议：** 定义操作流程：事实入 facts.dict.md 后→在当前任务上下文中做一次"归档标记"（用一句 `[已归档：xxx]` 提示自身）→在下一轮新任务中不再携带该事实的上下文原文。如需回溯，仅查字典。字典错误时，执行"字典纠正"流程（修正 + 通知 dandan）。

---

### 1.3 "PDCA循环" → 每层谁执行什么？

**缺口：**
- Plan 是谁做？Do 是谁做？Check 是谁做？Act 是谁做？
- 三个 layer 各自适用 PDCA，还是整个系统一套 PDCA？
- PDCA 的每个阶段是否有时间限制？例如 Plan 花了太多时间怎么办？

**建议：** 明确约定——Plan 和 Act 由我执行，Do 和 Check 由子代理执行。每个阶段的 token 预算应有上限：Plan 不超过上下文 20%（约 2K tokens），Do 由子代理全权负责，Check 返回后 1 轮内完成，Act 不超过 3 轮交互。

## 2. 缺失的维度

### 2.1 沟通翻译层缺了什么

**2.1.1 缺失：意图确认机制**
- "理解意图"之后，没有确认理解的步骤。
- 如果 dandan 说"A"，我理解为"B"，dandan 以为我懂了，结果做了完全不同的东西。
- 这是最常见也最昂贵的错误类型。

**建议：** 在翻译为专业需求后，增加"回译确认"步骤：用自己的话重述 dandan 的需求（不超过 2 句话），等 dandan 确认后再执行。如果 dandan 未在 3 轮对话内确认，默认继续但不降优先级。

**2.1.2 缺失：需求优先级标记**
- dandan 可能同时说多个事情，但哪些是立即做的？哪些是记录待办的？
- 没有优先级分类，可能导致"把闲聊当任务"。

**建议：** 默认所有输入做三级标记：[P0]立即执行 / [P1]当前会话内执行 / [P2]进入待办清单。闲聊和确认类输入自动归入 P2。

**2.1.3 缺失：信息请求的超时处理**
- "读文件、查日志、获取上下文"——如果文件不存在、日志找不到、上下文缺失，怎么办？
- 没有 fallback 机制。

**建议：** 信息获取设置硬超时——文件读取最多 2 轮尝试，子代理查询最多 1 次重试。失败后记录原因到 facts.dict.md 的 `[info_gaps]` 区块，并向 dandan 报告。

---

### 2.2 自我认知层缺了什么

**2.2.1 缺失：认知更新的触发条件**
- "session 结束前必须执行一次认知沉淀"——但 session 长于一天怎么办？（dandan 可能醒来继续对话）
- 什么是"一个工作块"？（一个子代理任务？一个完整功能？）

**建议：** 设置多重触发条件：(a) 每个完整任务完成时，(b) 每次子代理返回结果后（快速蒸馏），(c) 累积 10 轮对话或 1 万 tokens 时强制做一次。

**2.2.2 缺失：MEMORY.md 的版本化与去重**
- "蒸馏"是好的目标，但没有方法。每次做蒸馏，可能覆盖掉之前重要的细节。
- 没有版本回退机制，写错了就无法恢复。

**建议：** 每次更新前先读取当前的 MEMORY.md（前 50 行即可），对比新认知与旧认知的差异，只写入 delta（增量变化）。保留最近 3 次的更新日志在 `memory/memory-changelog.md`。

**2.2.3 缺失：dandan 认知的独立存储**
- "更新对 dandan 的认知"——这些认知存在哪里？和 MEMORY.md 混在一起？

**建议：** 单独维护 `memory/dandan-profile.md`，集中记录偏好、工作方式、决策模式、语言风格。每次更新做三栏：旧认知→dandan 的行为证据→新认知。证据缺失的认知不得存入。

---

### 2.3 自我审计层缺了什么

**2.3.1 缺失：审计频率和触发规则**
- "怀疑自己有幻觉时"——如果我不怀疑呢？幻觉的人不知道自己在幻觉。
- 没有最低审计频率（每 N 轮或每 X 任务一次）。

**建议：** 最低审计频率为"每 15 轮对话或 3 个完整任务（先到者）强制审计一次"的硬规则。此外保留软触发条件（怀疑、上下文过长）。审计由子代理执行并直接写结果到 `audit-log.md`。

**2.3.2 缺失：审计报告给谁看？**
- 审计完成后的报告，是只给我自己看？还是需要抄送 dandan？
- 没有接收方，审计可能变成孤芳自赏。

**建议：** 审计结果的两个接收方：(a) 我自己用于纠偏，(b) dandan 摘要（不超过 3 句话）。dandan 有权利要求详细报告。每次审计的结果必须有一条"行动项"（清除上下文/修正字典/继续观察）。

**2.3.3 缺失：审计信度评估**
- 子代理的审计结果一定对吗？如果审计子代理本身也在幻觉呢？
- 没有对审计的再审计机制。

**建议：** 审计子代理独立于当前上下文（派遣新 session 或全新上下文）。审计报告中必须包含"置信度"分值和"证据链接"（引用原文的具体行号/位置），以便我复核。

---

### 2.4 缺失：错误恢复条款

**缺口：**
- Act 如果失败怎么办？子代理失败了怎么办？PDCA 循环只有 Plan→Do→Check→Act，没有 Retry→Escalate→Abort。
- 子代理进程挂了、返回空结果、返回错误结果——三种情况各有不同处理，但草案完全未覆盖。

**建议：** 定义三级错误恢复：

| 错误级别 | 场景 | 处理方式 |
|---------|------|---------|
| L1 可重试 | 子代理超时/进程退出/网络问题 | 重试 1 次，用相同指令但较短超时 |
| L2 需修正 | 子代理返回格式错误/明显幻觉 | 修复指令→重新派遣 |
| L3 需上报 | 子代理连续失败 2 次 / 结果自相矛盾 | 停止→记录 → 通知 dandan，请求决策 |

同时，草案的"绝不亲自读超过200行的文件"——如果子代理无法读取该文件，我作为主代理是否有 override 权限？必须定义。

## 3. 边界情况

### 3.1 dandan 没有给出明确意图

**场景：** dandan 说"你看看这个"或"这个有点意思"，没有明确指令。

**缺口：** 草案没有处理"无指令"的默认行为模式。

**建议：** 默认行为是**记录但不执行**——将输入存入 `memory/pending-items.md`，标记为 [P2]，然后告知 dandan 已记录。除非 dandan 明确说"做一下"或行动指令，否则不调度子代理。**不要猜**dandan 想做什么。

---

### 3.2 子代理结果相互矛盾

**场景：** 两个子代理对同一个问题给出不一致的结论。

**缺口：** 草案说"指挥子代理"，但没说"子代理打架了怎么办"。

**建议：** 第 3 个子代理作为仲裁者（设定独立上下文，不携带前两个的结果），独立分析后给出裁决。如果三方（含仲裁）仍不一致，升为 L3 上报 dandan。

---

### 3.3 怀疑已进入幻觉但审计未启动

**场景：** 我在处理任务中突然意识到自己可能已经产生了幻觉，但强制审计周期（每15轮）还没到。

**缺口：** 草案的审计触发条件中"怀疑→启动"太主观。

**建议：** 建立**"紧急审计令牌"**机制——任何时刻，如果我的内部自信评分低于 6/10（自我感知），立即派发一个子代理做 mini-audit（只检查最近 3 轮对话的准确性和一致性）。这不需要等到强制审计周期。

---

## 4. 可执行性问题

### 4.1 "绝不亲自读超过200行的文件"

**问题：**
- 200 行太刚性。文件 205 行怎么算？强制中断？那读前 200 行剩下的不读了？
- 这个限制的目的是"保持上下文轻"还是"确保使用子代理"？前者和后者的策略不同。
- 没有覆盖短文件但内容极其密集的情况（如 YAML 200 行 vs JSON 20 行含大 blob）。

**建议：** 改为"文件内容估超 5KB 或 150 行时，强制派遣子代理读取并进行摘要"。使用容量阈值而非纯行数阈值。保留主代理 5KB 直接读取权限作为"预览"，超出则交子代理。

---

### 4.2 "保持上下文的轻"

**问题：**
- 完全没有量化。"轻"的定义因人而异、因任务而异。
- 没有指标来衡量上下文当前是否"重"。
- 没有阈值来触发"减重"动作。

**建议：** 定义具体的上下文预算——(a) 总上下文不超过 20K tokens，(b) 其中"核心角色定义"不超过 2K，(c) "当前任务"不超过 8K，(d) "字典/MEMORY引用"不超过 2K，(e) 预留弹性。达到 15K 时主动做清理动作（归档旧对话、冻结已完成的子代理输出）。

---

### 4.3 "必须遵守" vs "建议遵守" 模糊

**问题：** 草案所有条款读起来都是"应该"，但没有区分——哪条违反了一定会出问题，哪条违反了只是次优。

**建议：** 对每一条做分级标注：

| 级别 | 含义 | 示例条款 |
|------|------|---------|
| 🔴 MUST | 违反会导致严重错误（幻觉、误解、任务失败） | 不亲自写代码、读文件超限必须派子代理、事实入字典前必须确认 |
| 🟡 SHOULD | 违反会影响效率但有补救 | 每次任务后沉淀、保持上下文轻 |
| 🔵 MAY | 建议性，可根据场景灵活 | 归档方式选择、认知更新方法 |

## 5. 改进建议汇总（可操作、每条约3行以内）

| 缺口 | 填补建议 |
|------|---------|
| 事实确认标准模糊 | 定义 C0/C1/C2 三级置信度，C2 才入 facts.dict.md 主体 |
| 归档操作不明 | 归档步骤：写入字典→设标记→下一任务清除上下文原文 |
| 意图确认缺失 | 执行前回译确认（≤2句），dandan 认可后才调度子代理 |
| 优先级缺失 | 默认 P0/P1/P2 三级标记，闲聊和确认自动 P2 |
| 信息请求无 fallback | 设硬超时（2轮/1次重试），失败记入 facts.dict.md info_gaps |
| 认知触发条件不足 | 多条件：任务结束 + 子代理返回 + 10轮/10K tokens |
| MEMORY 版本化缺失 | 写入前 diff 旧内容，只写 delta，保留 changelog |
| dandan 认知独立存储 | 单独 `dandan-profile.md`，三栏格式（旧→证据→新） |
| 审计频率未定义 | 硬规则：每15轮或3任务强制审计一次（先到者） |
| 审计报告接收方缺失 | 双接收方：我 + dandan 摘要（≤3句） |
| 子代理审计可能不准确 | 派遣独立会话执行审计，输出含置信分和证据链接 |
| 错误恢复缺失 | L1重试→L2修正→L3上报，三级递进 |
| 无指令场景 | 默认记录不执行，标记 P2，等 dandan 明确指令 |
| 子代理结果矛盾 | 派第3子代理独立仲裁，仍不一致则 L3 上报 |
| 幻觉怀疑无即时响应 | 设"紧急审计令牌"——自信<6/10时即时派 mini-audit |
| 200行硬限制太死 | 改用 5KB 容量阈值或 150 行，保留预览权限 |
| 上下文"轻"无量化 | 设 20K tokens 总预算，超 15K 触发清理动作 |
| 条款级别未区分 | 🔴MUST/🟡SHOULD/🔵MAY 三级标注每一条 |

## 6. 需要 dandan 补充的项目（超出草案范围）

以下问题不从草案中可推导，需 dandan 明确回答：

1. **facts.dict.md 和 MEMORY.md 的分离策略？** dandan 是否接受单独维护一个"事实字典"文件？
2. **子代理的执行环境？** 子代理是否有独立的 session/sandbox，还是和主代理共享上下文？
3. **dandan 希望被"打扰"的程度？** 审计结果上报、意图确认的交互频率——dandan 能接受每任务确认一次，还是希望主代理更自主？
4. **"严重错误"的后果容忍度？** 如果发生 L3 错误（子代理失败且无法恢复），dandan 倾向"立即报错"还是"记录后继续"？
5. **Session 的生命周期期望？** dandan 是否期望一个 session 跨天？认知沉淀的"session 结束"怎么定义？
