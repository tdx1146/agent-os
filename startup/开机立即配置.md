## 二、模型配置：1M 上下文 + Thinking

### 2.1 contextWindow → 1M

DeepSeek v4 原生支持 **1M token** 上下文。OpenClaw 默认配置是 200K，**必须手动改到 1M**。

**配置文件位置：**
`/vol1/@apphome/trim.openclaw/data/home/.openclaw/openclaw.json`

**修改内容：**
```json
{
  "models": {
    "providers": {
      "DeepSeek": {
        "api": "openai-completions",
        "baseUrl": "https://api.deepseek.com",
        "models": [
          {
            "id": "deepseek-v4-flash",
            "name": "deepseek-v4-flash",
            "input": ["text"],
            "contextWindow": 1000000,
            "maxTokens": 16384,
            "reasoning": true
          },
          {
            "id": "deepseek-v4-pro",
            "name": "deepseek-v4-pro",
            "input": ["text"],
            "contextWindow": 1000000,
            "maxTokens": 16384,
            "reasoning": true
          }
        ]
      }
    }
  }
}
```

**改动说明：**

| 字段 | 旧值 | 新值 | 原因 |
|------|------|------|------|
| `contextWindow` | 200000 | **1000000** | DeepSeek v4 原生支持 1M |
| `maxTokens` | 8192 | **16384** | 文档显示最大支持 384K，16384 是保守值 |
| `reasoning` | 缺失(默认false) | **true** | 支持 thinking 模式的前提 |

> ⚠️ **重要**：`contextWindow` 不改成 1M → 上下文很快填满 → 频繁触发 compaction → compaction 中的 memory flush 锁写文件 → 你以为系统坏了其实是限制太窄。**根因不是写限制，是上下文太小。**

### 2.2 Thinking 模式

当前实例只有 DeepSeek + Astron 两个 provider。Astron 是纯代码模型无 reasoning，DeepSeek V4 支持 `thinking`。

**配置路径：**

```json
{
  "agents": {
    "defaults": {
      "thinkingDefault": "medium"
    }
  }
}
```

**Thinking 级别对照表（仅 DeepSeek V4 相关）：**

| 指令 | 效果 |
|------|------|
| `/think off` | 关闭 thinking |
| `/think minimal` / `/think low` | 低级别 thinking |
| `/think medium` | 中级 thinking（推荐默认） |
| `/think xhigh` | 对应 DeepSeek `reasoning_effort: "max"` |
| `/think max` | 同 xhigh，最高推理预算 |

**session 级操作：**
- 发一条纯指令消息 `/think medium` → 当前 session 立即生效
- 发 `/think default` → 清除 session 覆盖，继承全局默认
- 发 `/think`（无参数）→ 查看当前 thinking 级别

**配置生效优先级（从上到下）：**
1. `/t high` 内联指令（仅该消息）
2. 纯指令消息（session 级覆盖）
3. `agents.defaults.thinkingDefault`（全局默认）
4. 模型 provider 自带默认（`reasoning: true` 时默认 medium）

> ⚠️ 注意：当前实例用 DeepSeek API 直连，thinking 的非 off 级别在 DeepSeek 上意味着额外推理开销。`medium` 是平衡质量和成本的选择。

### 2.3 没有热重启就能生效

OpenClaw 的 `models.providers.*` 和 `agents.defaults` 配置都是 **hot-reload**（`reloadKind: "hot"` 或 `"none"`），改文件后无需重启 Gateway。

验证方式：

```bash
openclaw config validate
openclaw config get models.providers.DeepSeek.models
openclaw config get agents.defaults.thinkingDefault
```

## 三、Cron 任务配置

### 3.1 什么是 cron（OpenClaw 语境）

OpenClaw 的 cron 是 **Gateway 内置的任务调度器**，不是 Linux crontab。通过 `cron` 工具或 CLI 管理。

### 3.2 基本配置

```json
{
  "name": "任务名称",
  "schedule": {
    "kind": "cron",
    "expr": "0 23 * * *",
    "tz": "Asia/Shanghai"
  },
  "payload": {
    "kind": "agentTurn",
    "message": "提示语..."
  },
  "sessionTarget": "isolated"
}
```

**关键字段说明：**

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 任务唯一标识 |
| `schedule.kind` | 是 | `cron` / `at` / `every` |
| `schedule.expr` | cron时必填 | 标准 cron 表达式，**写上海时区** |
| `schedule.tz` | 否 | IANA 时区；不填则用 Gateway 本地时区 |
| `payload.kind` | 是 | `systemEvent`（主session）或 `agentTurn`（独立） |
| `payload.message` | agentTurn时必填 | 任务提示语 |
| `sessionTarget` | 否 | `"isolated"`（推荐） / `"main"` / `"current"` |

### 3.3 lightContext

```json
{
  "payload": {
    "kind": "agentTurn",
    "message": "...",
    "lightContext": true
  }
}
```

**效果：** 跳过 workspace bootstrap 文件（AGENTS.md / SOUL.md / TOOLS.md / IDENTITY.md / USER.md / HEARTBEAT.md / BOOTSTRAP.md）的注入。

- ✅ **减少每次 cron 执行的上下文**，节省 token
- ✅ 适合纯执行类任务（写文件、跑脚本、读数据）
- ❌ 会丢失 AGENTS.md 中的工作方式指南——如果任务需要指令，请在 `message` 中写明
- lightContext **不限制模型上下文窗口长度**（仍然是 1M）

### 3.4 isolated session

```json
{
  "sessionTarget": "isolated"
}
```

**效果：** 完全独立 session，每次执行新建会话。

- ✅ **不继承主会话上下文**（独立 token 预算、独立 transcript 文件）
- ✅ 不影响主会话的 compaction 状态
- ✅ 可同时跑多个 cron 任务不互相干扰
- ❌ 不能访问主会话的变量、记忆、文件（但能读硬盘上任何路径的文件）
- ❌ 每次执行都是全新的环境，没有"上次状态"

### 3.5 注意事项与陷阱

| 问题 | 表现 | 原因 | 解决 |
|------|------|------|------|
| **上下文白烧** | `isolated` + 轻任务但 token 消耗大 | `lightContext: false` 时注入了一堆 bootstrap 文件 | 轻任务务必 `lightContext: true` |
| **重复执行** | 任务跑了多次 | 没设 `deleteAfterRun` 的话 `at` 任务不会自动删除 | `at` 任务设 `deleteAfterRun: true` |
| **孤立会话残留** | cron session 不自动清理 | 默认 retention 24h | 用 `cron.sessionRetention` 缩短 |
| **工具限制** | exec/write 不能用 | `sessionTarget: "main"` 时受主 session sandbox 限制 | 用 `isolated` |
| **投递干扰** | cron 结果发到用户频道 | 没设 `delivery.mode: "none"` | 任务写文件而非投递消息时设 `mode: "none"` |

## 四、Senior Assistant Orchestrator 技能

### 4.1 是什么

一个 **OpenClaw 内置技能**（installed skill），定义了主 AI 的工作协议。它不是插件、不是配置，是一套**行为指南**注入到系统提示中。

### 4.2 安装位置（两个版本）

| 版本 | 路径 | 说明 |
|------|------|------|
| 原始版 | `workspace/skills/senior-assistant/SKILL.md` |  早期版本（仅供参考） |
| **正式版** | `workspace/skills/senior-assistant-orchestrator/SKILL.md`（275行） | **已应用的最新版本** |

workspace/skills 目录 → OpenClaw 加载顺序中**最高优先级**（load order 1）。

### 4.3 核心内容

- **角色定义**：主 AI 是常驻的，子 AI 是临时工
- **三层框架**：对上/对内/对下
- **PDCA 循环**：每次任务都有计划-执行-检查-改进
- **架构原则**：不重复、不发明轮子、控制复杂度
- **子 AI 指挥规范**：清晰的 objective/write-scope/verification 三要素
- **dandan 工作方式**（v2.2 补充）：
  - 她讨厌表演性帮助 → 直接给结论
  - 快速迭代 → 先共识方向再深入
  - 珍惜上下文 → 大量用子 AI
  - 后向兼容 → 文件体系确保新 AI 无缝接手

### 4.4 如何更新

```bash
# 通过 skill_workshop 工具
skill_workshop action=update skill_name=senior-assistant-orchestrator ...
```

不能直接修改 `workspace/skills/` 下的 SKILL.md 文件——必须走 `skill_workshop`。
